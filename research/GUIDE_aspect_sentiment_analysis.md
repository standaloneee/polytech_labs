## Что делает этот ноутбук?

Ноутбук решает задачу **анализа тональности** (sentiment analysis) русскоязычных отзывов на товары. Простыми словами: программа читает отзыв покупателя и определяет, положительный он, отрицательный или нейтральный.

Ноутбук состоит из двух больших частей:

1. **Сравнение трёх готовых моделей** — какая лучше определяет тональность
2. **Аспектный анализ тональности (ABSA)** — определение тональности не всего отзыва целиком, а по отдельным аспектам (качество, цена, доставка и т.д.)

---

## Зачем всё это нужно? (Смысл исследования)

### Проблема, которую мы решаем

Представь, что у интернет-магазина 100 000 отзывов. Читать их вручную нереально. Нужен автоматический инструмент, который:
- Определит, доволен покупатель или нет
- Поймёт, **чем именно** доволен или недоволен (доставкой? качеством? ценой?)

Это позволяет бизнесу быстро реагировать на проблемы и улучшать свой продукт.

### Почему мы сравниваем модели, а не обучаем свою?

В NLP (обработке естественного языка) есть два подхода:
1. **Обучить модель с нуля** — дорого, нужны данные и мощные GPU
2. **Использовать готовую предобученную модель** — быстро и бесплатно

Мы идём по второму пути: берём модели, которые кто-то уже обучил на русских отзывах, и проверяем, какая работает лучше. Это типичный подход для прикладных задач — зачем изобретать велосипед, если уже есть готовые решения?

### Почему именно три модели?

Эти три модели выбраны не случайно — они представляют разные компромиссы:

| Модель | Размер | Особенность |
|---|---|---|
| `blanchefort/rubert-base-cased-sentiment-rurewiews` | 178 млн параметров | Обучена именно на датасете RuReviews (наш тестовый датасет) |
| `sismetanin/rubert-ru-sentiment-rureviews` | 178 млн параметров | Тоже RuBERT-base, но от другого автора, с другими гиперпараметрами |
| `seara/rubert-tiny2-russian-sentiment` | 29 млн параметров | **В 6 раз меньше**, значит быстрее, но потенциально хуже |

Мы хотим понять: **стоит ли маленькая модель того?** Если она лишь немного хуже, но в 17 раз быстрее — для продакшна это может быть лучший выбор.

### Зачем нужен ABSA, если есть обычный sentiment analysis?

Обычный sentiment analysis даёт **одну оценку на весь отзыв**. Но отзывы часто содержат смешанные мнения:

> "Платье красивое, но пришло через 2 месяца, и размер не совпадает"

- **Внешний вид** → POSITIVE
- **Доставка** → NEGATIVE
- **Размер** → NEGATIVE

Обычная модель скажет: NEGATIVE или NEUTRAL. Но бизнесу важно знать, что с самим товаром всё ок — проблема в логистике и размерной сетке. ABSA даёт эту детализацию.

### Логика всего ноутбука (пошаговый план)

```
1. Подготовка → Скачать данные, загрузить модели
2. Тестирование → Прогнать 10 000 отзывов через каждую модель
3. Оценка → Посчитать метрики (accuracy, F1, время)
4. Визуализация → Графики и матрицы ошибок для наглядности
5. ABSA → Извлечь аспекты из отзывов и оценить тональность каждого
6. Анализ ABSA → Найти расхождения, противоречия, закономерности
7. Выводы → Какая модель лучше и для чего
```

### Что такое HuggingFace?

**HuggingFace** — это платформа (сайт huggingface.co), где люди выкладывают обученные модели машинного обучения. Можно скачать готовую модель и сразу использовать, не обучая её самому. Это как магазин приложений, только для моделей ИИ.

### Что такое метрики?

**Метрики** — это числовые показатели, по которым мы оцениваем, насколько хорошо модель работает. Например:
- **Accuracy** (точность) — процент правильных ответов из всех ответов
- **F1-score** — среднее между precision и recall (объяснено ниже)
- **Precision** — из всех отзывов, которые модель назвала "позитивными", сколько реально позитивных?
- **Recall** — из всех реально позитивных отзывов, сколько модель нашла?
- **Время инференса** — сколько времени модель тратит на обработку одного отзыва
- **Размер модели** — сколько параметров (числовых весов) в модели

**Что такое прокси (proxy)?** Прокси-сервер — это посредник между твоим компьютером и интернетом. В корпоративных сетях (на работе, в университете) интернет часто ходит через прокси. Это может мешать скачиванию моделей с HuggingFace.

**Что такое переменные окружения?** Это глобальные настройки операционной системы — пары "имя=значение". Программы читают их, чтобы узнать настройки системы. `os.environ` — это словарь (dict) всех переменных окружения.

**Что такое `sys.modules`?** Это словарь всех загруженных модулей Python. Когда ты делаешь `import pandas`, Python добавляет `pandas` в `sys.modules`.

`list(sys.modules.keys())` — создаём копию списка ключей, потому что нельзя менять словарь во время итерации по нему.

```python

except Exception:
    pass
```

**Что такое `try/except`?** Конструкция для обработки ошибок. Код в блоке `try` выполняется, и если произойдёт ошибка — выполнится блок `except`, а программа не упадёт. `pass` означает "ничего не делать".

**Что такое `lambda`?** Это анонимная (безымянная) функция. `lambda: False` — это функция, которая ничего не принимает и всегда возвращает `False`. Эквивалент:

### Часть 5: Патч httpx

```python
try:
    import httpx
    httpx._config.DEFAULT_TIMEOUT_CONFIG = httpx.Timeout(60.0)
    _original_client_init = httpx.Client.__init__
    def _patched_client_init(self, *args, **kwargs):
        kwargs.pop('proxy', None)
        kwargs.pop('proxies', None)
        kwargs['verify'] = False
        _original_client_init(self, *args, **kwargs)
    httpx.Client.__init__ = _patched_client_init
except ImportError:
    pass
```

**Что такое httpx?** Это HTTP-клиент, который использует `huggingface_hub` для скачивания моделей.

**Что такое патч (monkey-patch)?** Это подмена функции или метода во время выполнения программы. Мы сохраняем оригинальный `__init__` (конструктор) класса `httpx.Client`, а потом подменяем его на свою версию, которая:

1. Удаляет настройки прокси (`kwargs.pop('proxy', None)`)
2. Отключает проверку SSL (`kwargs['verify'] = False`)
3. Вызывает оригинальный конструктор

**Что такое `*args` и `**kwargs`?**
- `*args` — все позиционные аргументы в виде кортежа (tuple)
- `**kwargs` — все именованные аргументы в виде словаря (dict)

Это позволяет принять любые аргументы, не зная заранее, какие они будут.

## Ячейка 3 — Описание датасета (Markdown)

### Почему именно этот датасет?

Для того чтобы сравнить модели, нам нужны данные с **известными правильными ответами**. Мы не можем просто дать модели отзывы и поверить ей на слово — нужно проверить, совпадают ли её ответы с реальностью.

**RuReviews** идеально подходит, потому что:
- Это **русскоязычные** отзывы (наши модели обучены на русском)
- Каждый отзыв **уже размечен** — есть правильный ответ (positive/negative/neutral)
- Датасет **сбалансированный** — по 30 000 отзывов каждого класса
- Он **публичный и бесплатный** — можно скачать с GitHub

### Почему берём подвыборку 10 000, а не все 90 000?

- 10 000 отзывов — это статистически достаточно для надёжных выводов
- Прогон 90 000 отзывов через 3 модели занял бы слишком долго (особенно на CPU)
- Мы берём сбалансированную подвыборку (по ~3333 на класс), чтобы ни один класс не доминировал

Текстовая ячейка описывает датасет **RuReviews**:

- **Датасет** — это набор данных для обучения или тестирования моделей
- **RuReviews** — ~90 000 отзывов на женскую одежду с российского e-commerce сайта
- Датасет **сбалансированный** — в нём поровну отзывов каждого класса (по 30 000)
- **Три класса**: negative (отрицательный), neutral (нейтральный), positive (положительный)
- Для эксперимента берём **подвыборку 10 000 отзывов** — этого достаточно для статистически значимых результатов

### Что значит "сбалансированный"?

Если бы у нас было 80 000 положительных и 10 000 отрицательных отзывов, модель могла бы просто всегда отвечать "положительный" и иметь 80% accuracy. Сбалансированный датасет (поровну каждого класса) защищает от этого.

## Ячейка 12 — Вычисление метрик

### Зачем нужны разные метрики?

Может показаться, что достаточно одной accuracy (процент правильных ответов). Но это не так.

**Пример:** Модель на 100 отзывах:
- Из 50 реально позитивных назвала позитивными 45 (пропустила 5)
- Из 50 реально негативных назвала негативными 40 (10 ошибочно назвала позитивными)

Accuracy = (45+40)/100 = 85% — звучит неплохо. Но:
- **Precision** для positive = 45/(45+10) = 81.8% — из всех "позитивных" ответов модели 18.2% ошибки
- **Recall** для positive = 45/50 = 90% — модель нашла 90% позитивных отзывов
- **F1** = 2 × (0.818 × 0.9) / (0.818 + 0.9) = 0.857

Каждая метрика показывает своё, и для бизнеса важны разные вещи. Например, если мы фильтруем негативные отзывы для службы поддержки — важен recall для NEGATIVE (чтобы не пропустить жалобу).

```python
metrics_data = []

for model_name, result in results.items():
    predictions = result['predictions']

    accuracy = accuracy_score(true_labels, predictions)
```

`accuracy_score(y_true, y_pred)` — сравнивает два списка: правильные ответы и предсказания. Возвращает долю совпадений. Например, если из 100 отзывов модель угадала 85 — accuracy = 0.85.

```python
    precision, recall, f1, _ = precision_recall_fscore_support(
        true_labels, predictions, average='weighted', zero_division=0
    )
```

**precision_recall_fscore_support** — вычисляет 4 значения:
- **Precision** (точность) — "из тех, кого модель назвала positive, сколько реально positive?"
- **Recall** (полнота) — "из всех реально positive, сколько модель нашла?"
- **F1-score** — гармоническое среднее precision и recall: `2 * (P * R) / (P + R)`
- `_` (support) — количество примеров каждого класса. Подчёркивание `_` означает "нам не нужно это значение"

**`average='weighted'`** — усредняет метрики по классам с учётом их размера. Если классы сбалансированы, то `weighted` ≈ `macro`.

**`average='macro'`** — простое среднее по классам, без учёта размера. Macro честнее, если классы разного размера.

**`zero_division=0`** — если делитель ноль (ни одного предсказания класса), вернуть 0 вместо ошибки.

## Ячейка 14 — Детальные отчёты по классификации

### Зачем детальный отчёт, если метрики уже есть?

Ячейка 12 дала нам **усреднённые** метрики (одно число на всю модель). Но это скрывает важные детали. `classification_report` показывает метрики **для каждого класса отдельно**.

Например, модель может отлично определять POSITIVE (F1 = 0.94), но плохо отличать NEUTRAL от NEGATIVE (F1 = 0.72). Это критически важная информация — она говорит, что модель "путается" между нейтральными и негативными отзывами. ## Ячейка 25 — Описание ABSA (Markdown)

Начинается вторая часть ноутбука — **Aspect-Based Sentiment Analysis (ABSA)**.

### Зачем нужна вторая часть, если мы уже сравнили модели?

Первая часть отвечает на вопрос: "Какая модель лучше определяет ОБЩУЮ тональность?" Но в реальности бизнесу часто нужна **детализация**: не просто "отзыв негативный", а "клиент недоволен доставкой, но доволен качеством товара".

Вторая часть показывает, как можно **переиспользовать** уже существующую модель (которая умеет определять тональность текста) для более сложной задачи — аспектного анализа.

### Подход: rule-based + ML

В ABSA-части используется **гибридный подход**:
1. **Rule-based** (правила): извлечение аспектов по ключевым словам (словарь)
2. **ML** (машинное обучение): определение тональности каждого аспекта с помощью модели

Почему не чистый ML? Потому что для полностью ML-подхода к ABSA нужна специальная модель, обученная именно на аспектном анализе. Таких моделей для русского языка мало. Гибридный подход — это прагматичное решение, которое работает "уже сейчас".

### Что такое ABSA?

Обычный sentiment analysis определяет общую тональность текста. Но отзыв может содержать и хорошее, и плохое:

> "Доставка быстрая, но качество ужасное"

- **Обычный анализ**: NEUTRAL (среднее между хорошим и плохим)
- **ABSA**: Доставка = POSITIVE, Качество = NEGATIVE

ABSA выделяет **аспекты** (доставка, качество, цена, сервис) и определяет тональность **каждого аспекта отдельно**.

## Ячейка 27 — Определение категорий аспектов

### Как работает извлечение аспектов?

Идея простая: у нас есть **словарь** — для каждой категории (Качество, Цена, Доставка и т.д.) заданы ключевые слова. Мы ищем эти слова в тексте отзыва. Если нашли — значит отзыв упоминает этот аспект.

Это **rule-based подход** (основанный на правилах) — самый простой способ извлечения аспектов. У него есть ограничения:
- Может пропустить аспект, если покупатель использовал слово, которого нет в словаре
- Может неправильно определить аспект при многозначности слов

Но для демонстрации подхода и учебных целей это работает хорошо.

```python
import re
from collections import defaultdict
```

- `re` — модуль для **регулярных выражений** (поиск паттернов в тексте)
- `defaultdict` — словарь, который автоматически создаёт значение по умолчанию для несуществующего ключа

```python
ASPECT_KEYWORDS = {
    'Качество': [
        'качество', 'качественн', 'хорош', 'отличн', ...
    ],
    'Сервис': [...],
    'Цена': [...],
    'Скорость/Время': [...],
    'Упаковка/Внешний вид': [...],
}
```

Это **словарь аспектов**. Для каждой категории (Качество, Сервис и т.д.) определён список ключевых слов.

**Почему слова обрезаны?** Например, `'качественн'` вместо `'качественный'`. Это сделано для покрытия разных форм слова: "качественный", "качественная", "качественное", "качественно" — все начинаются с "качественн". Это примитивная форма **стемминга** (приведения слова к основе).

## Ячейка 29 — Аспектный анализ тональности

### Ключевая идея ABSA в этом ноутбуке

Вот как это работает пошагово:

1. Берём отзыв: *"Доставка быстрая, но качество ужасное"*
2. Ищем ключевые слова → нашли "быстр" (Скорость/Время) и "ужасн" (Качество)
3. Для каждого аспекта находим предложение, где он упомянут
4. Подаём это предложение в модель sentiment analysis
5. Модель говорит: "быстрая доставка" → POSITIVE, "качество ужасное" → NEGATIVE

**Хитрость:** мы не обучали новую модель для ABSA. Мы **переиспользовали** модель общего sentiment analysis, просто подавая ей не весь отзыв, а конкретное предложение про аспект. Это умный приём — делаем сложную задачу простыми средствами.

### Функция анализа тональности аспекта

```python
def analyze_aspect_sentiment(text, aspect_context, sentiment_model):
```

Подаём в модель не весь отзыв, а только **предложение с упоминанием аспекта**. Так модель оценит тональность именно этого фрагмента.

3. **Тональность vs количество аспектов** — "Связано ли количество упоминаемых аспектов с общей тональностью?" → Негативные отзывы чаще содержат больше аспектов (люди подробнее описывают, что не понравилось)
4. **Круговая диаграмма согласованности** — "Как часто общая тональность совпадает с аспектной?" → Показывает, насколько ABSA даёт дополнительную информацию по сравнению с обычным анализом

4 графика (2x2):

1. **Частота аспектов** — горизонтальная столбчатая диаграмма (`barh` = bar horizontal)
2. **Средняя уверенность модели** — для каждого аспекта

```python
aspect_avg_scores = defaultdict(list)
for result in aspect_results:
    for aspect, sentiment in result['aspects'].items():
        aspect_avg_scores[aspect].append(sentiment['score'])
avg_scores = {aspect: np.mean(scores) for aspect, scores in aspect_avg_scores.items()}
```

## Ячейка 38 — Сравнительная таблица

### Зачем сравнивать общую и аспектную тональность?

Это ключевой вопрос ABSA: **даёт ли аспектный анализ что-то новое по сравнению с обычным?**

Если общая и аспектная тональность всегда совпадают — ABSA бесполезен. Но если есть расхождения — значит ABSA выявляет информацию, которую обычный анализ упускает.

Результат: значительная часть отзывов имеет разногласия — общая тональность говорит одно, а аспекты — другое. Это доказывает ценность ABSA-подхода.

```python
has_disagreement = len(aspect_labels) > 1 or (
    len(aspect_labels) == 1 and aspect_labels[0] != result['overall_sentiment']
)
```

Разногласие есть, если:
- У разных аспектов разная тональность (POSITIVE и NEGATIVE в одном отзыве), ИЛИ
- Все аспекты имеют одну тональность, но она не совпадает с общей тональностью отзыва

## Ячейка 40 — Отзывы с противоречивой тональностью

### Почему это самый интересный результат?

Отзывы, где один аспект положительный, а другой отрицательный — это **главный аргумент в пользу ABSA**. Обычный sentiment analysis не может адекватно обработать такой отзыв: он вынужден выбрать одну оценку на весь текст. ABSA показывает полную картину.

Пример из реальных данных:
- Отзыв: *"Красивое платье, но доставка два месяца"*
- Обычный анализ: NEUTRAL (усредняет хорошее и плохое)
- ABSA: Внешний вид = POSITIVE, Доставка = NEGATIVE

Для бизнеса разница огромная: проблема не в товаре, а в логистике.

Ищем отзывы, где одновременно есть положительные И отрицательные аспекты:

```python
if 'POSITIVE' in unique_sentiments and 'NEGATIVE' in unique_sentiments:
    mixed_sentiment_reviews.append(...)
```

Для первого такого отзыва строится визуализация — горизонтальная столбчатая диаграмма, где цвет столбца зависит от тональности аспекта.

```python
from matplotlib.patches import Patch
legend_elements = [
    Patch(facecolor='#2ecc71', label='Positive'),
    ...
]
ax.legend(handles=legend_elements, loc='lower right')
```

`Patch` — цветной прямоугольник для легенды. Это нужно, потому что у каждого столбца свой цвет, и стандартная легенда не работает.
